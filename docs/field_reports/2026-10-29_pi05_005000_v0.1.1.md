## 요약

- **fr5_teleop 0.4.2의 그리퍼 완료 판정은 이 그리퍼에서 항상 실패한다.** `GetGripperMotionDone`은
  `[1, status]`를 돌려주고, status는 Robotiq gOBJ와 같은 뜻이다(0 움직임, 2 물체 잡고 멈춤, 3 목표 위치
  도착). 0.4.2는 `status == 1`만 완료로 보므로 빈손 닫기·열기(3)와 큐브 잡기(2)가 모두 5 s 뒤
  `gripper_timeout`이 된다. 첫 값 1은 fault가 아니다(컨트롤러 `gripper_fault`는 0).
- 그리퍼 자체는 정상이다. 끝까지 닫히고, 오류·알람이 없다(작업자 확인).
- 이전 동작의 완료가 남는 문제는 없다. 명령 14~16 ms 뒤 첫 poll부터 status 0이다. 따라서
  **`status != 0`을 완료로 보면** 완료가 실제 동작 끝(빈손 약 1.8 s, 큐브 약 1.3 s)에 맞는다.
- 움직이는 동안 CNDE `gripper_position`은 0이고, 완료 뒤 0.1~0.3 s 동안 최종값으로 따라온다.
  10-29의 "그리퍼 직후 관측 gripper 값이 항상 0.00"은 이것으로 설명된다.
- 규칙 5에 따라 코드는 고치지 않았다. 수정 제안은 맨 끝 절에 있다.
- 3-3 shadow: RTC를 켜면 4090에서 지연 p50이 135.5 → 169.4 ms(+34 ms)로, 300 ms 미만이다.
  이음매 튐 p50은 49.3 → 9.5 mm로 줄었다(shadow 참고값). RTC는 15/16 추론에 적용됐다.

## 3-2. 그리퍼 단독 점검: 실패

### G1 첫 `close` (`gripper_check.py`)

```
action close -> position 100 (velocity 70, force 50)
gripper position before: 1
MoveGripper call returned after 14 ms
first poll 14 ms after the command: done=False fault=1
NOT DONE within action_timeout_s 5.0 s (would be gripper_timeout)
  from  0.01 s  done=0 fault=1  position 0 -> 89
gripper position after: 89
```

- 작업자: 그리퍼는 끝까지 닫혔다. 펜던트·컨트롤러에 오류·알람 없음.
- `fault=1`이 나와 지시서에 따라 중단했다. G1의 나머지, G2, G3은 `gripper_check.py`로 하지 않았다.

### 진단 1: 정지 상태 읽기 (명령 없음)

`FairinoRobotClient.connect()`만 하고(`initialize` 없음) 0.2 s 간격으로 10회 읽었다. 그리퍼는 닫힌 채였다.

```
raw (0, [1, 3]) | pkg motion_done 3 fault 0 fault_id 0 active 1 pos 89 speed 0 cur 0   (10회 모두 같음)
```

SDK의 `GetGripperMotionDone`은 XML-RPC 결과 `[err, a, b]`를 그대로 `(err, [a, b])`로 돌려준다
(값의 의미는 SDK 코드에 없다). 두 번째 값은 CNDE `gripper_motion_done`과 같다. 첫 값 1은 CNDE
`gripper_fault`(0)와 다르다.

### 진단 2·3: 동작 중 상태 (그리퍼만 움직임, 작업자 동의)

`connect()` 후 `initialize` 없이 `move_gripper()`를 보내고 20 ms마다 읽어 값이 바뀔 때만 출력했다.
진단 3은 작업자가 펜던트로 큐브(테이블 위)를 손가락 사이에 두었다.

### 판정

| status (두 번째 값) | 관찰 | 뜻 (Robotiq gOBJ와 같음) | 0.4.2 판정 |
|---|---|---|---|
| 0 | 명령 직후부터 동작 끝까지 | 움직이는 중 | 미완료 (맞음) |
| 2 | 큐브를 잡고 멈춤, pos 59 | 닫다가 물체 감지 | **미완료 → `gripper_timeout`** |
| 3 | 빈손 닫힘 89, 열림 1 | 목표 위치 도착, 물체 없음 | **미완료 → `gripper_timeout`** |
| 1 | 이번에 나오지 않음 | 열다가 물체 감지 | 완료 |

| 지시서 기대 (3-2) | 결과 |
|---|---|
| `MoveGripper` 100 ms 미만 | 통과 (14~16 ms) |
| 첫 poll `done=False` | 통과 (status 0). 이전 완료가 남지 않음 |
| `done after` 0.5~1.5 s | **실패** (`NOT DONE`). status 기준 실제 완료는 빈손 1.78·1.82 s, 큐브 1.28·1.32 s |
| 닫힘 약 89, 열림 약 0~1 | 통과 (89, 1) |
| G3 큐브 위치 약 59~60, `fault=0` | 위치 59 통과. 0.4.2 판정으로는 `NOT DONE`·`fault=1` |

- G2(완료 시점과 실제 멈춤 비교)는 하지 않았다. status 기준 완료 시각과 작업자 체감의 비교는 수정
  뒤에 다시 한다.
- 빈손 동작 1.8 s는 지시서의 약 1.1 s보다 길다. 큐브를 잡을 때는 1.3 s다(손가락 이동 거리가 짧다).

### 관측 gripper 값

- 움직이는 동안 CNDE `gripper_position`은 **0**이다.
- status가 바뀐 순간의 위치는 최종값이 아니다(닫기 47 → 59, 열기 7 → 1). 0.1~0.3 s 뒤에 따라온다.
- 10-29의 "그리퍼 직후 관측 gripper 항상 0.00"의 원인으로 보인다. 완료 판정을 고쳐도 완료 직후의
  관측은 최종값보다 작거나 클 수 있다.

## 3-3. shadow: 4090에서 RTC 지연: 통과

로봇은 홈(TCP `[393.28, -122.64, 503.47]`, 펜던트로 작업자가 이동), 큐브는 시연 위치. 조건마다 컨테이너를
새로 띄우고 **정책 시작** → 10 s 뒤 **정지**(API). 두 회 모두 `stopped_by_operator`로 끝났다.

| 항목 | H1 RTC 끔 | H2 RTC 켬 (horizon 10) |
|---|---|---|
| run | `runs/20261029_171439_shadow` | `runs/20261029_171632_shadow` |
| 모델 로드 / GPU | 63.6 s / 9.66 GB | 68.5 s / 9.76 GB, `rtc_warmup_s` 0.15 |
| latency p50 / p90 / max | 135.5 / 142.1 / 146.7 ms | **169.4 / 188.4 / 203.6 ms** |
| switch jump p50 / p90 / max | 49.3 / 81.6 / 90.9 mm | **9.5 / 14.3 / 24.0 mm** |
| rtc guided | 0/15 | 15/16, delay steps [0, 5, 6] |
| cmd speed p50 / max | 75.0 / 76.2 mm/s | 75.0 / 76.4 mm/s |
| cmd − tcp p50 / max | 32.0 / 62.8 mm | 39.3 / 67.5 mm |
| tick p99 / max | 9.84 / 10 ms | 9.32 / 12 ms |

- 지시서 기대(`rtc guided` n−1/n, 지연 +약 30 ms, 300 ms 미만)를 모두 만족한다. 지연 증가는 +34 ms.
- shadow는 로봇이 움직이지 않아 매 추론이 홈에서 다시 계획된다. switch jump와 cmd − tcp는 참고값이다.
- H2 뒤 `policy.rtc.enabled: false`로 되돌렸다.

## 개발 PC 후속 작업 제안

1. **fr5_teleop `FairinoRobotClient.get_gripper_motion_state`**
   - 완료: `status != 0` (1·2·3 모두 멈춤).

   - `tests/unit/test_fairino_adapter.py`의 v0.4.2 테스트를 이 값(`[1, 0]`, `[1, 2]`, `[1, 3]`)으로 바꾼다.
